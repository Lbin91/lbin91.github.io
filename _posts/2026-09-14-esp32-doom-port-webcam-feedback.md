코드를 한 줄도 손대지 않고 ESP32 개발보드에 둠(Doom)을 포팅했다는 글이 r/LocalLLM에 올라왔다. 하룻밤 새 퍼진 이야기라기보다는, 사흘간의 시행착오가 고스란히 담긴 기록이다. 읽다 보면 이 사람이 결국 찾아낸 게 모델의 성능이 아니라는 점이 재미있다. 피드백 루프다.

## 무엇을 했나

u/Sulya_be는 개발자가 아니다. 본인 말로는 그냥 바이브 코딩으로 장난치는 사람이라고 한다. 세팅은 이렇다. RTX 5090 위에서 LM Studio로 Qwen 3.8 27B를 돌리고, 하네스는 OpenCode Desktop. ESP32 기반의 Cheap Yellow Display, 그러니까 몇천 원짜리 LCD 달린 보드에 게임을 올리려고 했다. 목표는 하나, 사람이 코드에 손대지 않는 것.

처음엔 실패했다. GBA용 둠 소스를 주고 포팅을 시도했는데 이틀을 쏟아붙은 결과물은 동작하긴 했으나 색이 다 깨져 있었다. 그리고 여기서가 이야기의 핵심인데, 하루 더 디버깅을 하다가 그는 멈췄다. 왜냐. 화면이 뭘 보여주는지 모델에게 알려줄 방법이 없었기 때문이다. 색이 어떻게 잘못됐는지 확인하려면 본인이 스크린 사진을 마흔 장 넘게 찍어서 채팅창에 붙여넣어야 했다.

## 바뀐 것 하나: 웹캠

재도전에서 그가 바꾼 건 두 가지다. 원본 둠 소스를 줬고, 그리고 PC에 웹캠을 연결해 ESP32 화면을 비추도록 놓은 뒤 "화면에 뭐가 뜨는지 알고 싶으면 이 카메라를 봐라"고 알려줬다.

```
# 대략 이런 구조
LLM --코드--> ESP32 (둠 실행)
ESP32 화면 --> 웹캠 --> LLM이 다시 확인
```

이건 단순한 편의 장치가 아니다. 모델 입장에서 눈이 생긴 셈이다. 자기가 쓴 코드가 실제 하드웨어에서 어떻게 보이는지 스스로 확인하고, 그걸 근거로 다음 수정을 판단할 수 있게 됐다.

결과는 세 시간도 안 걸렸다. 보드 화면에 둠 타이틀이 떴다. 처음엔 터치스크린이 안 됐지만 "터치가 안 된다"고 알려주자 나아졌고, 시리얼로 조작하는 것은 그냥 잘 됐다.

나중에 밝혀진 사실 하나. GitHub에 있던 GBA→ESP32 포팅 코드를 모델이 찾아내서 상당 부분 그걸로 해결했다. 부정행위냐고 할 수도 있지만, 나는 이것도 능력이라고 본다. 필요한 자원을 찾아 쓰는 것까지 포함해서 코딩 에이전트가 해야 할 일이니까.

## 진짜 흥미로운 부분은 세션 로그

그가 세션 기록을 스크롤하면서 발견한 것들이 이 글의 백미다. 모델은 WAD 파일이 플래시에 안 들어간다는 걸 알자 스트리밍 대신 파일을 전략적으로 잘라 넣었다. SD 카드에서 읽고 캐싱하는 방식은 느리다는 판단이었다. 또 터치스크린과 SD 카드가 SPI 버스를 공유한다는 걸 파악하고, 터치를 소프트웨어 SPI로 돌려 속도를 확보할까 고민하다가 그냥 SD 카드를 버리는 쪽을 택했다.

이런 결정들은 어지간한 임베디드 초보자보다 낫다. 하드웨어 제약을 이해하고, 트레이드오프를 저울질하고, 실행 가능한 쪽으로 접는다. 모델 크기는 27B다. 프런티어급이 아니어도 이 정도 판단이 나온다는 게, 로컬 모델로도 충분히 재밌는 걸 할 수 있다는 실례다.

## 왜 주목할까

AI 코딩 이야기가 매일 쏟아지지만 대부분은 벤치마크 점수나 데모 영상 수준이다. 이 글이 다른 이유는 실패 사례와 성공 사이의 차이를 정확히 보여주기 때문이다. 같은 모델, 같은 하드웨어인데 결과가 갈렸다. 갈린 지점은 모델이 아니라 인간이 만들어준 환경이었다.

웹캠이라는 발상이 좀 우스워 보일 수 있다. 화면 캡처 도구를 쓰면 되지 않냐고도 할 수 있다. 맞는 말이지만, 임베디드 보드엔 화면 캡처 API 같은 게 없다. 있는 건 물리적 화면뿐이고, 그걸 읽는 가장 단순한 방법이 카메라였다. 로우테크 해결책이 하이테크 문제를 푼 셈이다.

또 하나. 검열되지 않은 모델 얘기가 같은 날 서브레딧에서 돌았는데, 거기 달린 댓글 중에 검열 해제가 성인용 콘텐츠 같은 것만이 아니라 일반 성능에도 도움이 된다는 얘기가 있었다. 지나친 자기검열과 과도한 사고 과정이 줄어든다는 것. 이번 둠 포팅이 검증한 건 그와 다른 차원의 교훈이다. 모델을 뭐로 고르느냐보다, 모델이 세상을 볼 수 있는 창을 어떻게 열어주느냐가 결과를 가른다.

## 정리

한 줄도 안 만지겠다는 규칙을 지키면서 둠을 보드에 올렸다. 세 시간 만에 됐다. 비결은 새 모델이 아니라 웹캠 하나였다. 자기 작업 결과를 스스로 볼 수 있는 에이전트와 그렇지 않은 에이전트의 차이가 이렇게 크다는 걸 보여주는 사례로, 올해 읽은 바이브 코딩 담 중에 손꼽히는 것 같다.

다음에 로컬 모델로 뭘 만들다가 막히면 모델을 바꾸기 전에 물어보자. 걔가 지금 뭘 보고 있는지. 어쩌면 눈만 만들어주면 해결될지도 모른다.
