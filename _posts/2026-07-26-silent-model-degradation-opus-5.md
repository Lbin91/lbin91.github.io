r/ClaudeCode에서 이상한 글이 연달아 올라왔다. "Opus 5가 출시될 것 같다"는 글과, 곧이어 "Opus 5가 이미 너프됐다?"는 글이었다. 아직 정식 출시도 하지 않은 모델인데, 벌써 성능이 떨어졌느냐는 물음이 나오고 있다.

웃기는 이야기 같지만, 사실 이보다 더 진지한 문제가 숨어 있다.

## "네가 쓰는 모델은 Opus 5가 아닙니다"

가장 흥미로운 건 댓글 반응이었다. 한 사용자는 Opus 5에게 질문하려 할 때마다 모델이 스스로 "Opus 5는 존재하지 않는다"며 Opus 4.8로 리디렉션한다고 적었다. 당신은 Opus 4.8 모델을 사용하고 있습니다. 이 말을 계속 되풀이한다. 사용자 표현을 빌리자면, 끊임없이 가스라이팅을 당하는 셈이다.

다른 사용자는 4.6이면 간단히 처리할 작업을 Opus 5에 맡겼는데, 모델이 작업을 시작하는 대신 세차에 관한 질문을 던지기 시작했다고 한다. 단순한 버그 같기도 하고, 컨텍스트 처리에 문제가 생긴 것 같기도 하다. 확실한 건 사용자가 혼란스럽다는 것.

그리고 "Opus 5는 4.9의 멍청한 버전에 불과하다"는 댓글도 달렸다. 출시 전부터 성능 하락을 체감하고 있다는 것.

## 조용히 바뀌는 모델, 들썩이는 커뮤니티

여기서 진짜 문제는 "Opus 5가 너프됐냐"가 아니다. 모델이 언제 바뀌었는지, 어떤 변경이 있었는지 아무도 모른다는 것. API 기반 서비스에서는 버전 명시가 가능하고, 변경 내역도 문서로 남는다. 하지만 채팅 인터페이스나 통합 에이전트 환경에서는 그런 게 없다. 오늘 잘 되던 작업이 내일은 안 된다. 이유는 묻지 못한다. 답도 안 온다.

이런 현상을 보통 silent degradation이라고 부른다. 성능이 조용히, 그러나 확실하게 내려가는 것. 사용자는 체감으로 알아챌 수 있지만, 공식 발표나 changelog가 없으니 "내가 잘못 쓰는 건가" 의심하게 된다. 심한 경우엔 모델이 직접 "나는 그 모델이 아니다"라고 부정하니까 더 혼란스럽다.

r/LocalLLM에서도 비슷한 맥락의 이야기가 나온다. 로컬에서 30B급 모델을 돌리는 사람들이 "간단한 작업은 상용 모델과 구별이 안 된다"고 말한다. 그러면서도 "에이전트 코딩 같은 복잡한 작업에서는 차이가 확 난다"고 덧붙인다. 로컬 모델은 적어도 양자화 수준이나 버전을 내가 정하니까 silent degradation 문제에서 자유롭다. 내가 Q4_K_M으로 돌리면 그건 Q4_K_M이다. 어제나 오늘이나.

## 검증 없이 쓴다는 것

좀 더 근본적인 질문을 던져보자. 우리는 왜 이걸 그냥 받아들이나?

모델 출력을 신뢰해서 코드를 작성하고, 자동화 파이프라인을 구축하고, 에이전트 루프를 돌린다. 그런데 그 모델이 어느 시점에 조용히 변경될 수 있다면, 쌓아온 시스템 전체의 신뢰성이 흔들린다. 어제까지 잘 돌아가던 자동화 스크립트가 갑자기 이상한 결과를 내기 시작하면, 디버깅부터 해야 한다. 모델 탓인지, 프롬프트 탓인지, 데이터 탓인지.

한 개발자는 200~600K 토큰을 소비하면서도 결과물이 엉망이라는 이야기를 r/ClaudeCode에 올렸다. "tokenmaxing과 successmaxing은 같지 않다"는 제목이었다. 많이 돌렸다고 좋은 결과가 나오는 게 아니라는 것. 그런데 토큰 소모량의 대부분이 캐시 읽기라는 지적도 달렸다. 숫자는 커 보이지만 실제 출력 토큰은 훨씬 적다. 성능 지표를 토큰 사용량으로 판단하면 안 된다는 교훈이다.

## 그래서 뭘 할 수 있나

완벽한 해결책은 없다. 하지만 몇 가지는 할 수 있다.

버전을 고정할 수 있는 환경에서는 고정한다. API를 직접 호출할 수 있다면 모델 버전을 명시하고, 변경 시점을 기록한다. 로컬 모델을 사용할 수 있는 영역에서는 로컬을 섞어 쓴다. 양자화 손실이 있더라도, 적어도 내가 통제할 수 있는 버전이라면 예측 가능하다.

출력 검증 루프를 만든다. 한 모델의 결과를 다른 모델로 교차 확인하는 패턴이 이미 널리 쓰인다. 앞서 소개된 jinn이나 codor 같은 멀티 에이전트 설정이 그런 접근의 연장선에 있다. Fable이 작성하고 Sol이 검토하는 구조가 왜 효과적인가. 서로 다른 모델이 독립적으로 평가하기 때문에, 한쪽의 조용한 성능 변화가 다른 쪽에서 포착될 확률이 높아진다.

그리고 커뮤니티 반응에 귀를 기울인다. Reddit 포럼이나 Discord 채널에서 "이상하게 오늘부터 결과가 이상하다"는 글이 여러 명에 의해 올라온다면, 그건 보통 개인의 착각이 아니다. 공식 발표를 기다리기보다 먼저 대응하는 편이 낫다.

## 정리

Opus 5가 진짜 너프됐는지는 알 수 없다. 어쩌면 출시 전 버전 혼란일 수도 있고, 실제로 무언가 바뀌었을 수도 있다. 중요한 건 특정 모델의 성능이 아니라, 우리가 모델을 얼마나 통제 가능한 상태에서 사용하고 있느냐는 문제다.

조용히 바뀌는 모델에 의존하는 한, silent degradation은 계속 일어난다. 발표 없이, 경고 없이. 대응은 개인의 몫으로 남는다. 버전을 기록하고, 교차 검증하고, 로컬을 섞어 쓰는 정도가 지금으로서는 가장 현실적인 방어선이다.
