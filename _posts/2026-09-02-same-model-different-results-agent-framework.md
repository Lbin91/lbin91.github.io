최근 Reddit r/zaiglm에서 흥미로운 실험 결과가 올라왔다. 같은 모델, 같은 프롬프트를 쓰는데도 프레임워크에 따라 비용과 품질이 크게 갈린다는 이야기다.

실험 조건은 단순하다. GLM 5.3 Flash 하나를 갖고 동일한 4개 작업 프롬프트를 OpenClaw 2.0과 Hermes라는 두 에이전트 프레임워크에서 각각 실행한 뒤, 소비 토큰과 비용, 자가수정 횟수를 비교했다. 모델이 같으니 결과 차이는 순전히 에이전트 설계에서 나온다는 게 이 실험의 요점이다.

## 숫자부터 보자

- OpenClaw 2.0: 토큰 2.1M, 비용 $4.50, 자가수정 10회
- Hermes: 토큰 2.9M, 비용 $4.00, 자가수정 20회

처음 보면 좀 이상하다. Hermes가 토큰을 38% 더 썼는데 비용은 오히려 쌌다. 어떻게 이런 일이 가능할까.

답은 토큰의 구성에 있다. LLM 과금은 입력과 출력 단가가 다른데, 보통 출력이 몇 배는 비싸다. OpenClaw는 매 턴마다 큰 컨텍스트를 다시 밀어 넣는 구조라 입력 토큰 비중이 높고, Hermes는 상대적으로 짧은 응답을 여러 번 생성하는 패턴이었던 것. 총량이 아니라 입출력의 비율이 최종 비용을 결정한다는, 알고는 있지만 실측 데이터로 확인하기 어려운 부분을 보여준 사례다.

## 자가 검증 전략이 결과를 바꾼다

더 흥미로운 지점은 자가수정 횟수다. Hermes는 20번을 고쳤고 OpenClaw는 10번이면 충분했다. 횟수 자체가 문제가 아니라, 뭘 기준으로 "틀렸다"고 판정하느냐가 갈렸다.

Hermes는 스크린샷 픽셀 카운트로 결과를 검증했다. 화면이 바뀌었는지 세어 보는 식이다. 반면 OpenClaw는 테스트 셋을 직접 구축해서 통과 여부로 판정했다. 픽셀 카운트는 싸고 빠르지만 오탐이 많아 불필요한 수정 루프를 돌게 만들고, 테스트 셋은 만들 때 비용이 들지만 한 번 만들어두면 판정이 명확하다. 자가수정 20회 vs 10회의 차이는 결국 이 검증 전략의 차이였던 셈이다.

에이전트가 스스로 결과를 점검한다는 건 좋게 들리지만, 점검 기준이 느슨하면 오히려 토큰을 태우며 제자리걸음을 반복한다. "얼마나 자주 검증하느냐"보다 "무엇으로 검증하느냐"가 중요하다는 걸 숫자로 보여준다.

## 왜 주목할까

요즘 코딩 에이전트 얘기를 하면 대부분 "어떤 모델을 쓰느냐"로 귀결된다. 벤치마크 순위를 들이밀며 이 모델이 낫다 저 모델이 낫다. 그런데 이 실험은 모델을 고정하고 프레임워크만 바꿨는데도 비용이 10% 넘게 갈리고 수정 루프가 두 배 차이 났다는 걸 보여준다.

실무에서 에이전트를 돌려본 사람이라면 공감할 부분이다. 같은 모델으로도 시스템 프롬프트 구성, 컨텍스트 관리 정책, 실패 판정 방식에 따라 하루 세션이 몇 배로 갈린다. 모델 선정에 쏟는 에너지의 절반만 에이전트 설계에 투자해도체감 성능은 더 크게 좋아질 수 있다는 얘기다.

동시에 이런 실측 데이터가 개인 사용자 레벨에서 공유되기 시작했다는 것 자체도 의미가 있다. 예전에는 벤더가 공식으로 내놓는 벤치마크가 거의 유일한 정보원이었다면, 이제는 커뮤니티에서 프레임워크 간 비교를 직접 측정해서 올린다. 구매 결정의 기반이 광고에서 경험 데이터로 옮겨가는 중이다.

## 정리

모델 성능이 에이전트 경험의 전부가 아니다. 이 실험에서 드러난 건 세 가지다. 총 토큰량보다 입출력 구성이 비용을 결정한다. 자가 검증의 기준이 느슨하면 수정 루프가 늘어 토큰만 태운다. 그리고 두 차이는 모델이 아니라 프레임워크 설계에서 나온다.

에이전트 도구를 고르거나 직접 만들 때, "어떤 모델을 물릴까" 이전에 "컨텍스트를 어떻게 쌓고, 결과를 무엇으로 판정할까"부터 따져보자. 그 편이 비용과 품질 모두에서 더 큰 레버가 되는 경우가 많다.
