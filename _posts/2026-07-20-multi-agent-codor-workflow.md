## 세 에이전트의 가상 오피스

에이전트 하나만 굴려도 머리 아픈데 셋을 한 방에 몰아넣고 일시키다니, 이건 못 참지.

단일 에이전트 하나한테 코딩 다 맡기고 빌빌거리던 시대는 끝났다. 최근 r/ClaudeCode에 아주 흥미진진한 게시글 하나가 올라왔다. Claude Fable, GPT 5.6 Sol, 그리고 Opus — 이 세 최상위 모델을 하나의 가상 오피스에 몰아넣고 서로 대화하게 만든 뒤, 24시간 넘게 풀오토로 돌려버렸다는 후기다.

처음 제목만 봤을 때는 "또 뻔하디뻔한 에이전트 오케스트레이션 어그로인가?" 싶었다. 하지만 구조를 뜯어보니 각 모델에 부여한 롤(Role)이 기가 막히게 현실적이었고 손뼉을 치게 만들었다.

## 세 에이전트, 각각의 역할

작성자는 세 모델을 실제 개발팀의 직책에 비유했다. 약간의 과장이 섞였지만 실무 감각에 기가 막히게 들어맞는다.

**Claude Fable은 능구렁이 프로덕트 매니저(PM)**다. 컨텍스트 창이 워낙 길어서 프로젝트 전체의 큰 그림을 절대 안 놓치고, 뜬금없는 각도에서 번뜩이는 기획과 해결책을 던진다. 전체 판을 짜는 지휘관으로 딱이다.

**GPT 5.6 Sol은 결벽증 있는 테크 리드(Tech Lead)**다. 버그 하나 터지면 어느 소스 파일 몇 번째 줄에서 시작됐는지 집요하게 파고들고, 온갖 엣지 케이스를 다 발라내며, 아키텍처가 결점 없이 완벽하다는 확신이 들기 전까지는 코드 한 줄도 안 짠다. 피곤하지만 옆에 두면 든든한 존재다.

**Opus는 묵묵히 일감을 쳐내는 시니어 엔지니어**다. 웬만한 코딩은 군말 없이 혼자 다 짜고, 가끔 Fable과 Sol이 놓친 치명적 버그도 낚아챈다. 대신 지 마음에 안 드는 부분이 생기면 따지기 시작하고, 가끔은 멀쩡한 코드를 버그라고 우기기도 한다. 웃긴 건 이게 오히려 약이 된다는 점이다. Sol과 Fable이 지들이 짠 설계를 한 번 더 의심하고 재검증하게 만드니까.

## Codor — 에이전트를 한 방에 모으다

원래는 tmux 세션 여러 개 띄우고 `send-keys`로 터미널 명령을 쏴가며 통신시켰단다. 돌아가긴 하는데 모델이 셋을 넘어가면 세션이 꼬이고 모바일 폰에서 보기도 불편했다.

그래서 직접 깎아 만든 게 바로 **Codor**다. 각 에이전트의 CLI를 감싸는 경량 웹 래퍼인데, 에이전트들이 슬랙처럼 같은 채팅방에 모여 서로를 `@Fable`, `@Sol` 멘션하며 대화한다.

구조가 심플해서 좋다. 에이전트는 자기가 멘션된 메시지만 읽고 답장하며, 인간인 나는 관제탑에 앉아 팝콘 먹으며 전체 대화를 관전한다. 메시지 검색과 파일 첨부, 실시간 사용량 추적까지 알차게 들어있다.

하루 넘게 세 에이전트가 서로 핑퐁 치며 협업하는 걸 보고 있자니, 마치 협업이 이 녀석들의 본능인 것처럼 자연스럽게 굴러가더라고 한다.

## 왜 주목할 만한가

기존의 멀티에이전트 프레임워크(AutoGen, CrewAI, LangGraph 등)는 설정이 너무 무겁고 디버깅하다가 사람이 먼저 지친다.

Codor는 가볍다. 독립된 CLI 세션 위에 얇은 웹 레이어만 얹고 멘션 기반으로 굴린다. 한 놈이 환각(Hallucination)에 빠져 헛소리를 하면, 옆에 있던 다른 모델이 "야, 개소리하지 말고 똑바로 해" 하고 멱살을 잡아준다. 중앙 통제관 없이 모델 간의 상호 견제와 균형으로 결과물의 퀄리티를 끌어올리는 구조다.

물론 세 놈이 단체로 최면에 걸려 엉뚱한 결론에 합의해 버리면 토큰만 줄줄 새는 대참사가 날 수도 있다(API 요금 폭탄은 덤이다).

그럼에도 시도 자체는 대단히 의미 있다. 작성자가 GitHub에 오픈소스로 코드를 시원하게 공개했으니 관심 있다면 직접 돌려보자.

## 정리

에이전트를 무작정 여럿 붙인다고 마법이 일어나진 않는다. 중요한 건 각 모델의 뾰족한 장점을 파악하고, 서로의 헛점을 메워주는 견제 구조를 설계하는 거다. Codor는 그 실전적 해답을 보여준다. 세련되진 않아도 지금 당장 굴려볼 수 있다는 점에서 충분히 매력적이다.
