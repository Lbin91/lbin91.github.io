매번 같은 프롬프트를 복붙하는 게 비효율적이라 느꼈다면, Anthropic이 제시하는 'Skill'이라는 개념이 정확히 그 답이 될 수 있다.

## 복붙의 한계

솔직히 말하면, 나도 한때 노션에 "잘 먹히는 프롬프트 모음"을 정리해뒀다. 코드 리뷰 시킬 때 쓰는 프롬프트, 블로그 글 다듬을 때 쓰는 프롬프트, PR 설명 작성 시킬 때 쓰는 프롬프트... 이런 식으로 모아두고 매번 복사해서 붙여넣곤 했다.

그런데 이게 혼자 쓸 때는 괜찮은데, 팀 단위로 가면 문제가 생긴다. 같은 "코드 리뷰" 업무인데 A는 보안 관점에서만 보고, B는 컨벤션만 체크하고, C는 아예 다른 포맷으로 결과를 뽑는다. 프롬프트가 제각각이니 결과물의 품질도 들쑥날쑥이다.

Anthropic이 최근 발표한 "A complete guide to building skills for Claude"라는 가이드가 딱 이 문제에 대한 이야기다. 읽어보니 꽤 흥미로운 접근이라 정리해봤다.

## 스킬(Skill)이란?

가이드에서 정의하는 스킬은 우리가 흔히 말하는 "프롬프트"와는 결이 다르다. 비유하자면 이런 차이다.

- **프롬프트**: "이 코드 리뷰해줘." (일회성 요청, 매번 넣어줘야 함)
- **스킬**: "우리 회사 보안 가이드라인과 변수 명명 규칙에 따라 코드를 점검하고, 발견된 이슈는 심각도(Critical/Major/Minor)에 따라 분류해서 리포트해." (재사용 가능한 절차)

결국 스킬은 Claude에게 '특정 작업을 수행하는 매뉴얼'을 통째로 넘기는 것이다. 신입 사원한테 업무 매뉴얼 쥐어주듯이, AI한테도 "이 상황에선 이렇게 해"라는 절차서를 줄 수 있게 만든 셈이다.

누가 사용하든 동일한 절차를 따르니까, 결과물의 품질이 일정해진다. iOS 개발에 비유하면 코딩 컨벤션 문서를 SwiftLint 규칙으로 바꾸는 것과 비슷한 맥락이랄까.

## MCP와 뭐가 다른 건데?

여기서 혼동하기 쉬운 게 MCP(Model Context Protocol)와의 관계다. 나도 처음엔 "MCP랑 비슷한 거 아닌가?" 싶었는데, 역할이 완전히 다르다.

- **MCP**: 연결을 담당한다. 데이터베이스, GitHub, Google Drive 같은 외부 도구와 데이터를 Claude에게 가져다주는 파이프라인. "여기서 데이터 가져와"에 해당.
- **Skill**: 절차를 담당한다. 가져온 데이터를 어떻게 가공하고, 분석하고, 보고할지 정하는 두뇌. "가져온 걸로 이렇게 처리해"에 해당.

실제 시나리오로 보면 감이 온다.

> 1. MCP가 사내 DB에서 '지난달 매출 데이터'를 가져온다.
> 2. Skill이 이 데이터를 '재무팀 주간 보고서 양식'에 맞춰 요약하고, 전월 대비 변동이 10% 이상인 항목은 별도로 플래그를 달아준다.

MCP 없이도 스킬은 쓸 수 있고(독립형), MCP와 결합하면 훨씬 강력해진다(강화형). 둘은 경쟁이 아니라 레고 블록처럼 조합하는 관계다.

## 기술적 구조: 폴더 하나가 스킬 하나

스킬의 물리적 형태는 생각보다 심플하다. 하나의 폴더 구조로 관리되고, Git으로 버전 관리하면 된다.

```
my-skill/
├── SKILL.md          # 스킬의 핵심 로직과 정의
├── templates/        # 보고서 양식, 이메일 초안 등
├── resources/        # 참고할 사내 규정, 가이드라인
└── examples/         # Few-shot learning용 예시
```

핵심은 `SKILL.md` 파일인데, 여기에 스킬의 트리거 조건, 실행 절차, 출력 형식 등을 정의한다.

그런데 `SKILL.md`의 `description` 메타데이터가 좀 독특하다. 이건 사람이 읽으라고 있는 게 아니라, Claude가 "아, 지금 이 스킬을 꺼내 써야겠다"고 판단하는 트리거 역할을 한다. description을 얼마나 잘 쓰느냐에 따라 스킬이 적절한 타이밍에 발동될 수도 있고, 영영 안 불릴 수도 있다.

또 하나 눈에 띄는 건 '점진적 공개(Progressive Disclosure)' 패턴이다. 스킬의 모든 내용을 한꺼번에 로드하는 게 아니라, 상황에 따라 필요한 부분만 점진적으로 불러온다. 토큰 효율을 위한 설계인데, 이런 세부 사항에서 Anthropic이 실제 프로덕션 환경을 많이 고민했다는 게 느껴진다.

## 활용 패턴 두 가지

### 패턴 A: 독립형 스킬

외부 도구 없이 Claude의 기본 능력에 전문성을 입히는 방식이다.

내가 실제로 쓸 법한 예시를 몇 개 떠올려봤다:
- iOS 앱의 접근성(Accessibility) 체크리스트를 기반으로 코드 리뷰하는 스킬
- 우리 팀 코딩 컨벤션에 맞춰 Swift 코드를 점검하는 스킬
- 앱 스토어 심사 가이드라인에 맞춰 릴리즈 노트를 작성하는 스킬

### 패턴 B: MCP 강화 워크플로우

외부 데이터와 도구를 결합해서 복잡한 업무를 자동화하는 방식이다.

- Jira(MCP)에서 이번 스프린트 티켓을 조회 → 우선순위 재산정(Skill) → Slack(MCP)으로 팀 채널에 정리해서 공유
- GitHub(MCP)에서 PR 목록 가져오기 → 각 PR의 변경 사항을 보안 관점에서 분석(Skill) → 위험도가 높은 건 리뷰어에게 자동 알림

이 패턴을 보면서 느낀 건, 결국 AI 활용의 핵심이 '잘 물어보는 것'에서 '잘 설계하는 것'으로 옮겨가고 있다는 거다.

## 개인적인 생각

솔직히 아직은 개인 개발자 입장에서 스킬을 체계적으로 구축할 동기가 크지는 않다. 혼자 쓰는데 폴더 구조까지 잡아가며 관리하는 건 과한 느낌이다.

하지만 팀 단위로 보면 얘기가 다르다. "AI를 잘 쓰는 팀원"의 노하우를 스킬로 패키징해서 팀 전체에 배포할 수 있다는 건 꽤 매력적이다. 특히 온보딩 과정에서 신입 개발자한테 "이 스킬들 써봐"라고 건네줄 수 있다면, AI 활용 능력의 격차를 상당 부분 줄일 수 있을 것 같다.

이제 AI 활용은 "누가 프롬프트를 기가 막히게 잘 짜느냐"의 개인기에서, "누가 조직에 맞는 AI 워크플로우를 잘 설계하고 공유하느냐"의 엔지니어링 영역으로 넘어가는 중이다.

반복되는 작업이 있다면, 프롬프트 창을 열기 전에 `SKILL.md` 파일 하나 만들어 보는 것도 나쁘지 않겠다.
