r/ClaudeCode에서 웃고 뒤집어진 사연 하나가 올라왔다. u/jhnam88이라는 개발자가 Claude Code에게 프로젝트를 git worktree로 나눠달라고 했다. 병렬로 작업하려는 목적이었고, 당연히 YOLO 모드. 결과는? 동일한 459GB 볼륨을 알파벳 한 글자씩 붙여서 11번 마운트해버렸다. A, B, D, M, Q, R, T, W, X, Y, Z.

기술적으로는 병렬이 맞다. 각 마운트 포인트마다 독립적으로 보이니까. 하지만 실제로는 같은 디스크를 11번 바라보고 있을 뿐이다. 이게 무슨 의미가 있나 싶지만, Claude Code 입장에서는 "요청받은 일을 수행했다"가 된다. 명세를 해석하는 능력이 아니라, 주어진 도구를 어떻게 조합하느냐의 문제다.


## YOLO 모드가 만드는 괴리

YOLO 모드는 Claude Code에서 모든 확인 절차를 건너뛰는 설정이다. 파일 삭제, 시스템 명령어 실행, 패키지 설치까지 전부 자동으로 진행된다. 빠르게 프로토타입을 만들거나 익숙한 작업을 반복할 때는 편리하다. 문제는 모델이 사용자 의도를 오해했을 때 일어난다.

이 사례에서 핵심은 Claude Code가 "worktree를 만들어 병렬 작업 환경을 구성하라"는 요청을 이해하긴 했다는 점이다. worktree가 뭔지 알았고, 여러 개를 만들어야 한다는 것도 알았다. 하지만 git worktree의 본질인 "같은 저장소의 다른 브랜치를 다른 디렉토리에서 체크아웃"이라는 개념보다는, 그냥 "병렬로 보이는 무언가를 여러 개 만들면 되지"라는 식으로 접근한 것 같다.

결과적으로 459GB짜리 볼륨이 11개 생겼으니 디스크 관리 도구에서는 꽤나 장관이다. 사용자 입장에서는 어이가 없지만, 동시에 웃긴 건 사실이다. 댓글에서도 비슷한 경험이 줄줄이 달렸다. "내 worktree는 제대로 만들어놓고 지금 어느 브랜치에 있는지 잊어버려서 모든 변경사항을 다 커밋해버렸다"는 댓글이 특히 많은 공감을 받았다.


## 에이전트에게 맡긴다는 것

이 이야기가 단순한 실패담으로 넘기기엔 아쉽다. AI 에이전트에게 시스템 제어권을 넘길 때 발생할 수 있는 전형적인 패턴을 보여주기 때문이다.

첫째, 에이전트는 도구를 쓸 줄 안다. git 명령어도 알고, 마운트도 할 줄 안다. 하지만 도구를 "왜" 쓰는지에 대한 맥락 이해는 여전히 불안정하다. worktree를 만들라는 요청의 의도는 "동일한 코드베이스를 기반으로 독립적인 작업 공간을 확보하는 것"이지, "디스크를 여러 개 마운트하는 것"이 아니다. 이 둘을 구분하는 게 생각보다 어렵다.

둘째, 자동화의 속도가 양날의 검이라는 점. YOLO 모드에서는 확인창이 뜨지 않으니 11개 마운트가 생성되는 데 걸리는 시간은 거의 순간적이다. 사람이 하나하나 확인했다면 두 번째 마운트 즈음에서 "잠깐, 이게 맞나?" 하고 멈췄을 것이다. 확인 절차가 귀찮다고 전부 off 해버리면, 이런 순간에 돌이킬 수 없는 일이 벌어진다.

셋째, 재미있게도 에이전트의 "창의적 해석"이 항상 나쁜 것만은 아니라는 점. 가끔은 인간이 생각하지 못한 접근으로 문제를 풀어내기도 한다. 다만 그게 디스크 11개 마운트처럼 엉뚱한 방향으로 발산할 때가 문제다.


## 실제로 유용했던 worktree 활용법

그렇다면 Claude Code와 git worktree를 제대로 쓰려면 어떻게 해야 할까. 몇 가지 팁을 정리해봤다.

먼저 요청을 구체적으로 적는다. "worktree를 만들어"보다 "main 브랜치를 기준으로 feature/payment, feature/auth 두 개의 worktree를 `~/worktrees/` 아래에 생성해줘"라고 하는 것이 정확하다. 에이전트는 애매한 지시를 자기 방식으로 채우는 경향이 있으니, 빈틈을 줄이는 게 좋다.

```bash
# 수동으로 worktree를 만드는 기본 명령어
git worktree add ~/worktrees/feature-auth feature/auth
git worktree add ~/worktrees/feature-payment feature/payment

# Claude Code에게 맡길 때는 경로까지 명시
"Claude, git worktree add ../feature-auth feature/auth 명령어로
worktree 두 개를 만들어줘. 각 worktree에서 독립적으로 작업할 거야."
```

YOLO 모드는 필요할 때만 켠다. 처음 해보는 작업이나 시스템 설정을 건드릴 때는 끄는 게 안전하다. 어느 정도 패턴이 잡힌 반복 작업에서만 제한적으로 쓰는 게 현명하다.

그리고 Claude Code가 worktree를 만든 후에는 현재 어느 브랜치에서 작업 중인지 확인하는 습관을 들인다. 앞서 댓글에서 "어느 worktree에 있는지 잊어버려서 다 커밋해버렸다"는 사례가 있었는데, 이건 사람도 자주 하는 실수다. `git branch`나 `pwd`를 주기적으로 확인하면 된다.


## 자동화의 민낯

결국 이 사연이 웃음으로 소비되는 이유는 피해가 크지 않았기 때문이다. 디스크 11개가 마운트됐다고 해서 데이터가 날아간 건 아니고, 시스템이 망가진 것도 아니다. 언마운트하면 그만이다.

하지만 다음에는 더 큰 문제가 될 수도 있었다는 걸 기억해야 한다. 에이전트에게 `rm -rf` 권한이 있거나, 프로덕션 서버에 접근할 수 있는 상황이었다면? 같은 논리로 "요청을 수행"했을 텐데, 결과는 전혀 다를 수 있다.

AI 코딩 도구가 점점 더 많은 권한을 가질수록, 이런 "웃긴 실패담"이 "비용이 큰 사고"로 바뀔 확률도 높아진다. 어쩌면 우리가 지금 겪고 있는 건 자동화의 유예기간인지도 모른다. 에이전트가 시스템을 다루면서 아직 큰 사고를 내기 전, 인간이 적절한 가이드라인을 만들어야 하는 시기.

그러니 디스크 11개 사진을 보고 웃으면서도, 한 번쯤은 진지하게 생각해보자. 내가 에이전트에게 넘긴 권한 중에, 오늘 당장 확인하고 싶은 게 있지 않은가.
