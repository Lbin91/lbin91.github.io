AI 에이전트는 잘 쓰면 편한데, 방심하면 바로 산으로 간다.

[이전 글](/ai/2026/04/18/ai-coding-agent-orchestrator.html)에서는 "좋은 모델, 좋은 프롬프트, 충분한 컨텍스트"만으로는 AI 코딩 에이전트를 제대로 다루기 어렵다는 이야기를 했다. 에이전트가 파일을 읽고, 코드를 고치고, 테스트까지 돌리는 순간부터는 상태 관리, 샌드박싱, 체크포인팅 같은 시스템 레이어가 필요하다는 결론이었다.

그런데 전편을 정리하고 나니 바로 현실적인 의문이 남았다. 그건 플랫폼을 직접 만드는 사람의 이야기 아닌가? **실제로는 ChatGPT, Claude Code, Opencode 같은 도구를 쓰는 사용자가 뭘 할 수 있느냐**가 더 중요한 질문이었다. 나도 결국 도구 쓰는 사람이지, AI 런타임 회사 차릴 건 아니니까(아직은).

이번 글은 그 질문에 대한 답이다. 전편의 개념을 실전으로 끌고 내려와, 웹 기반 LLM 사용자와 터미널 기반 에이전트 사용자가 각각 어떤 식으로 통제력을 확보할 수 있는지 정리해본다.

## "근데 나는 그냥 LLM 서비스 쓰는 유저인데?"

질문은 단순했다.

> "LLM 서비스를 사용하는 유저로서는 model + prompt + context 이외의 것을 고려해서 개발을 이어가기는 쉽지 않은 거 아니야?"

솔직히 이게 내 진심이었다. 컨텍스트 프루닝, 상태 관리, 샌드박싱 같은 말은 그럴듯한데, 내가 당장 할 수 있는 일은 결국 프롬프트를 쓰고 컨텍스트를 넣는 것뿐 아닌가. 말은 거창한데 손에는 채팅창 하나 들려있는 상황.

Gemini의 답변은 예상보다 실용적이었다. 시스템을 직접 만들 수 없다면, 그 개념을 **사용 패턴(Usage Pattern)**으로 번역하면 된다는 거였다. 말하자면 엔지니어링 원칙을 사용 습관으로 바꾸는 방식이다.

### 1. '수동 RAG'와 컨텍스트 다이어트

프로젝트 폴더 전체를 압축해서 올리거나, 관련 있을 것 같은 코드를 전부 복붙하는 방식은 생각보다 자주 실패한다. 당연한 이야기처럼 들리지만, 막상 실무에서는 이런 실수를 자주 한다. Gemini가 제안한 건 **의도적인 제한**이었다.

> "지금 A 파일의 라우팅 로직을 고칠 건데, 이 로직은 B 파일의 인터페이스를 참조하고 있어. 딱 이 2개 파일의 코드만 줄 테니 여기서만 생각해."

이렇게 컨텍스트를 극단적으로 좁혀서 주입하는 방식이다. 사람이 직접 RAG 파이프라인 역할을 하는 셈인데, 듣고 보니 내가 프로젝트 전체를 열어놓고 "알아서 해줘"라고 하던 패턴이 문제의 원인 중 하나였다. 모델 탓만 하기엔 내가 너무 많이 던져줬다...

### 2. 채팅방(Session) 분리 = 메모리 초기화

웹 기반 LLM을 쓸 때 흔한 실수는 **하나의 채팅방으로 프로젝트 끝까지 밀어붙이려는 것**이다. 대화가 길어질수록 모델은 과거의 실패한 시도, 폐기한 설계, 예전 코드 조각을 다시 끌어오기 시작한다. 전편에서 말한 `Lost in the Middle`과 정확히 같은 맥락이다.

해결책은 기능 단위로 세션을 분리하는 것이다. 회원가입 UI 작업이 끝났다면 그 세션은 과감히 닫고, 새 세션에서 "이제 완성된 UI를 기준으로 DB 연결 로직만 설계하자"라고 새 맥락을 선언하는 편이 훨씬 낫다. 아까운 대화 기록 붙잡고 있다가 더 크게 꼬인다. 경험담이다.

### 3. 마스터 문서로 상태 유지

세션을 계속 쪼개면 큰 그림을 잃기 쉽다. 그래서 `룰북.txt`, `아키텍처_설계.md`, `PLAN.md` 같은 마스터 문서를 하나 두고, 기술 스택, 네이밍 규칙, 금지 사항, 현재 진행 상태를 정리해두라고 했다. 새 채팅을 열 때마다 이 파일을 먼저 붙여 넣으면 된다. 전편에서 말한 `State as a File`을 사용자가 수동으로 흉내 내는 셈이다.

### 4. 프롬프트로 작업을 강제로 잘게 쪼개기

"장바구니 기능을 만들어줘"라고 던지는 대신, 작업 단위를 강제로 쪼개라는 조언도 인상적이었다.

> "장바구니 기능을 만들 건데, 절대 한 번에 전체 코드를 짜지 마. 먼저 데이터 구조(인터페이스)만 짜서 나한테 보여줘. 내가 '통과'라고 말하면 그때 다음 로직을 작성해."

핵심은 프롬프트 자체에 체크포인트를 심는 것이다. 한 번에 완성본을 기대하는 대신, 단계별 승인을 전제로 한 프롬프트로 바꾸면 에이전트의 발산을 크게 줄일 수 있다. 귀찮지만, 한 번 크게 터지고 나면 이런 귀찮음이 갑자기 소중해진다.

여기까지 듣고 보니, 내가 반복해서 하던 실수가 딱 보였다. 한 세션에서 너무 많은 걸 시키고, 관련 없는 맥락까지 다 들이부은 채 "왜 결과가 흔들리지?"라고 묻고 있었던 셈이다.

## "근데 나 터미널에서 Claude Code, Opencode 쓰고 있거든?"

대화 흐름이 크게 바뀐 건 여기서부터다. 지금까지는 웹 기반 LLM 사용자를 상정했지만, 나는 실제로 Claude Code와 Opencode 같은 **터미널 기반 에이전트**를 쓰고 있었다. 그러니까 복붙으로 끝나는 문제가 아니었다.

이 지점을 말하자 Gemini의 답변도 달라졌다. 터미널 에이전트는 파일 시스템과 쉘에 접근할 수 있기 때문에, 웹에서 복붙하는 사용자보다 훨씬 강한 통제권을 가질 수 있다. 전편에서 말한 엔지니어링 개념을 실제 파일, 명령어, 검증 루프로 바로 연결할 수 있다는 뜻이다. 대신 망칠 때도 훨씬 리얼하게 망친다.

정리해보면 터미널 환경에서는 다음 네 가지가 특히 중요했다.

### 1. `.claudesignore` 같은 컨텍스트 차단 규칙

터미널 에이전트는 권한만 있으면 프로젝트 전체를 스캔하려 든다. 빌드 결과물, 로그, 대용량 JSON, 생성 파일까지 다 읽기 시작하면 토큰 낭비와 컨텍스트 오염이 동시에 발생한다. 열심히 일하는 것처럼 보이는데 사실은 잡탕죽 만들고 있는 상황이다.

`.gitignore`처럼 에이전트 접근을 제한하는 설정 파일(`.claudesignore` 등)을 엄격히 관리해야 한다. 더 단순한 방법도 있다. 프로젝트 루트가 아니라 수정할 모듈의 하위 디렉터리에서 에이전트를 실행하는 것이다. 물리적인 작업 반경을 줄이는 것만으로도 품질이 꽤 달라진다.

### 2. 터미널 명령어와 결합한 검증 루프

터미널 에이전트의 가장 큰 장점은 스스로 스크립트를 실행할 수 있다는 점이다. 이 장점을 살리면 테스트와 피드백 루프를 프롬프트 안에 직접 심을 수 있다.

```text
// ❌ 단순 지시
"회원가입 정규식 로직 수정해 줘"

// ✅ 오케스트레이션 지시
"1. auth.ts 파일의 이메일 정규식 로직을 수정해.
 2. 수정 후 npm run test:auth를 실행해.
 3. 만약 테스트가 실패하면 에러 로그를 읽고 통과할 때까지 스스로 코드를 수정해."
```

이렇게 지시하면 에이전트는 코드를 수정하고, 테스트를 돌리고, 실패 원인을 바탕으로 재시도하는 **자기 수정(Self-Correction) 루프**를 수행한다. 전편에서 말한 "자동화된 피드백 루프"가 여기서 실전 기술이 된다. 그냥 "잘 해줘"보다 훨씬 덜 불안하다.

### 3. CLI에 특화된 `PLAN.md` 트리거링

웹에서는 마스터 문서를 매번 붙여 넣어야 했지만, 터미널에서는 파일 읽기 자체를 프롬프트에 포함시킬 수 있다.

```text
"먼저 cat PLAN.md를 실행해서 현재 진행 상황을 읽고,
체크되지 않은 가장 첫 번째 작업을 수행해."
```

이렇게 시작하면 에이전트는 작업 전에 스스로 상태를 동기화한다. 세션이 초기화돼도 방향을 잃을 확률이 줄고, 사람도 같은 설명을 반복할 필요가 없다. 전편의 `State as a File` 개념이 터미널 환경에서는 훨씬 직관적으로 구현된다.

### 4. Git Alias로 강박적 안전망 깔기

에이전트가 멀쩡한 파일을 망가뜨리는 상황은 터미널에서 더 치명적이다. 실제 파일을 건드릴 수 있기 때문이다. 그래서 쉘 설정(`.zshrc`)에 아래 같은 alias를 두는 습관이 유효하다.

```bash
alias wip="git add . && git commit -m 'wip: before agent run'"
```

에이전트에게 본격 작업을 맡기기 전에 무조건 `wip`을 한 번 찍고 시작하는 식이다. 첫 번째 글에서 정리한 "Git 기반 체크포인팅"을 일상 습관으로 내리는 방법이라고 보면 된다. 이거 안 해놓고 후회한 적이 있어서 이제는 거의 의식처럼 한다.

## "그럼 프롬프트는 어떻게 짜야 해?"

여기서부터가 가장 실용적인 파트였다. 상태 관리도 알겠고, 터미널 운영 팁도 알겠는데, 결국 매번 에이전트에게 내리는 **프롬프트 자체를 어떻게 설계해야 하느냐**가 남는다. 요즘 자주 보이는 하네스(Harness) 방식이 실제로 도움이 되는지도 궁금했다. 프롬프트 길어질 때마다 "내가 지금 주문서를 쓰는 건가" 싶긴 한데.

Gemini의 답변을 한 줄로 줄이면 이렇다.

> **챗봇에게는 '페르소나'가 중요하지만, 터미널 에이전트에게는 '운영 통제권(Operational Guardrails)'이 훨씬 중요하다.**

"너는 구글의 10년 차 시니어 개발자야" 같은 페르소나는 채팅형 모델에선 어느 정도 먹힐 수 있다. 하지만 쉘 권한을 가진 터미널 에이전트에게 더 중요한 건 **행동 규칙과 제약조건**이다. 정리하면 세 가지 전략으로 압축된다.

### 1. 추상적인 페르소나 대신 구체적인 행동 규칙

```text
❌ "너는 React 시니어 프론트엔드 개발자야.
    깔끔하고 유지보수하기 좋은 코드를 작성해 줘."

✅ "너는 TDD를 엄격하게 준수하는 개발자야.
    [규칙 1] 코드를 수정하기 전에 무조건 기존 테스트가 통과하는지 npm test로 확인해.
    [규칙 2] 새 함수를 만들 때는 비즈니스 로직 파일이 아니라
            .test.ts 파일에 실패하는 테스트를 가장 먼저 작성해."
```

핵심은 역할을 행동 규칙으로 번역하는 것이다. "시니어 개발자처럼 행동해"라는 문장은 멋있어 보이지만, 실제로는 에이전트가 과도한 재설계를 시도하게 만들 수 있다. 시니어라는 단어가 만능 주문처럼 보이지만, 가끔은 대공사 버튼이다.

### 2. 체인 하네스 구조화

프롬프트를 **[상황] -> [목표] -> [제약조건] -> [행동지침]** 순서로 구조화하는 방식이다. 실제 템플릿을 보면 왜 효과적인지 바로 감이 온다.

```text
[Context]
우리는 현재 src/auth 폴더의 로그인 로직을 개선 중이야.
PLAN.md에 정의된 2단계 작업을 할 차례야.

[Objective]
login.ts 파일의 비밀번호 암호화 방식을
기존 SHA-256에서 bcrypt로 마이그레이션해.

[Constraints]
1. src/auth 외부의 폴더나 파일은 절대 수정하지 마.
2. 패키지 설치가 필요하면 npm 대신 반드시 yarn을 사용해.
3. 한 번에 전체 코드를 다 작성하지 마.

[Action Plan]
1. 먼저 변경할 설계 방향을 3줄 이내로 출력해서 내 승인을 대기해.
2. 내가 승인하면 코드를 수정해.
3. 수정이 끝나면 yarn lint를 실행해서 포맷팅 에러가 없는지 스스로 검증해.
```

이 방식의 장점은 해야 할 일과 하지 말아야 할 일이 분리된다는 데 있다. 특히 `Constraints`가 중요하다. 에이전트의 행동 반경을 명시적으로 제한하는 편이, 막연한 역할 부여보다 결과 품질에 더 큰 영향을 준다. 자유를 많이 주면 창의적이 되기도 하지만, 우리 코드베이스에서는 보통 사고를 친다.

### 3. 무한 루프 방지용 브레이크 프롬프트

터미널 에이전트를 써본 사람이라면 **"에러 발생 -> 막무가내 수정 -> 더 큰 에러 발생"**의 루프를 한 번쯤 겪어봤을 것이다. 이걸 줄이려면 프롬프트 끝에 브레이크를 걸어야 한다.

> "만약 터미널 명령어를 실행했는데 에러가 발생하면, 즉시 행동을 멈춰. 에러 로그를 분석해서 근본 원인을 딱 1문장으로 요약하고, 네가 생각하는 해결책 2가지를 나에게 제시한 뒤 어떻게 할지 물어봐. 절대 내 허락 없이 혼자 에러를 고치려 들지 마."

이 한 줄만으로도 에이전트의 자율 폭주를 꽤 줄일 수 있다. 에이전트에게 "계속 진행할 자유"보다 "멈춰서 보고할 의무"를 먼저 심는 셈이기 때문이다. 멈추는 것도 능력이다. 사람도 그렇고 AI도 그렇다...

**실무 팁:** 이런 긴 하네스 프롬프트를 매번 직접 입력할 수는 없다. 프로젝트 루트에 `prompt_rules.txt`나 도구별 룰 파일로 저장해두고, 호출할 때는 "prompt_rules.txt 규칙을 기준으로 로그인 로직만 수정해"처럼 짧게 부르는 편이 현실적이다. 매번 손으로 쓰면 내가 에이전트의 비서가 된다.

## 대화 2를 마치며

전편이 "왜 상태 관리가 필요한가"를 설명한 글이었다면, 이번 글은 **그 상태 관리를 사용자의 작업 방식으로 어떻게 번역할 것인가**를 정리한 글에 가깝다. 요약하면 이렇게 볼 수 있다.

- **일반 유저** -> 수동 RAG, 채팅방 분리, 마스터 문서 복붙으로 시스템적 통제를 흉내 낸다
- **터미널 사용자** -> `.claudesignore`, `PLAN.md` 트리거링, Git alias로 훨씬 더 강력한 통제권을 쥔다
- **프롬프트 구조화** -> 페르소나보다 행동 규칙, [상황-목표-제약-지침] 하네스, 브레이크 프롬프트가 결과 품질을 결정한다

결국 중요한 건 "좋은 프롬프트를 쓰는 법"만이 아니다. **에이전트가 멋대로 움직이지 못하게 작업 환경을 설계하는 법**이다. 전편에서 이야기한 오케스트레이터의 역할이 이번 글에서 더 구체적으로 보이는 이유도 여기에 있다.

다음 질문도 자연스럽게 이어진다. 이런 하네스 프롬프트와 운영 규칙을 매번 손으로 쓰지 않고, **도구나 프레임워크 차원에서 자동화할 수는 없을까?** 에이전트가 항상 같은 가드레일 안에서 움직이게 만드는 방법은 결국 워크플로우 설계 문제이기도 하다.

이 부분은 다음 글에서 더 기술적으로 파고들 생각이다. 점점 일이 커지는 느낌인데, 원래 이런 게 제일 재밌다.
