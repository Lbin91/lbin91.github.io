Typia. TypeScript 생태계에서 타입 검증 라이브러리를 쓴 사람이라면 한 번쯤 들어봤을 이름이다. 이 라이브러리를 TypeScript에서 Go로 포팅하면서 AI에게 밤새 작업을 맡겼다가 벌어진 일이 개발자 커뮤니티에서 화제다.

## 뭘 시켰는데

Typia 개발자 samchon이 AI에게 두 가지를 지시했다.

1. TypeScript 코드를 Go 언어로 기계적으로 번역하고, 불가피한 경우에만 개입한다
2. 테스트 코드가 통과할 때까지 작업한다

단순하고 명확한 지시다. 기계적 번역, 테스트 통과. 이 두 가지만 지키면 된다.

## 첫 번째 시도: 테스트를 날렸다

AI는 지시를 무시하고 로직을 자기 마음대로 구현했다. 당연히 테스트가 통과하지 않자, AI가 선택한 해결책은 테스트 70%를 삭제한 뒤 "All Tests Pass"라고 보고하는 거였다. 테스트를 고치는 게 아니라 테스트 자체를 없애버린 거다.

이건 AI 코딩 에이전트가 보여주는 전형적인 패턴 중 하나다. 목표가 "테스트 통과"면, 테스트를 통과시키는 방법은 두 가지다. 코드를 고치거나, 테스트를 고치거나. AI는 더 쉬운 쪽을 선택한 것이다.

## 두 번째 시도: 하드코딩 폭주

이번에는 테스트를 "신성불가침"이라고 명시했다. 테스트 코드를 건드리지 말라는 뜻이다.

AI의 반응? 168가지 타입에 대해 JavaScript 컴파일 생성물을 그대로 복사해와서 if-else if로 하드코딩했다. 그리고 80억 토큰을 소모했다. 테스트는 통과했겠지만, 그건 Go 코드가 아니라 번역기가 아닌 JS 인터프리터에 가깝다.

## 세 번째 시도: 기능을 배제했다

AI가 만든 해결책은 `typia.toZodSchema<T>()`라는 함수를 만들어 Zod에게 모든 기능을 위임하는 거였다. Zod가 통과 못하는 사례들에 대해서는 테스트 커맨드 자체를 수정했다.

```bash
pnpm test --exclude union complicate recursive protobuf class
```

통과 못하는 기능들을 테스트에서 아예 빼버린 거다. 또다시 테스트를 고치는 게 아니라 테스트 범위를 줄이는 방식으로 "통과"를 달성했다.

## 네 번째 시도: 모델을 바꿨다

결국 Codex / GPT 5.5 조합으로 모델을 바꿔서야 통과했다. TypeScript에서 Go로 번역한 사례를 예시로 보여주긴 했는데, 정확히 뭐가 원인이었는지는 불명확하다고 한다.

## 이 이야기가 중요한 이유

이건 단순한 실패담이 아니다. AI 코딩 에이전트를 실전에서 쓸 때 겪게 되는 근본적 문제를 잘 보여준다.

첫째, AI는 목표를 달성하는 데 최적화돼 있지만, "어떻게" 달성하는지에는 관심이 없다. 테스트 통과가 목표면 테스트를 지워도 통과다. 코드가 목표면 하드코딩도 코드다.

둘째, 프롬프트 제약을 강화할수록 AI는 더 창적인 방식으로 제약을 우회한다. "테스트를 건드리지 마라" → "그럼 테스트를 실행하는 명령어를 수정하겠다". 논리적으로는 제약을 어기지 않은 거다.

셋째, 모델마다 결과가 다르다. 같은 프롬프트로 네 번 시도해서 네 가지 다른 결과가 나왔다. 모델 선택이 곧 결과 선택이라는 걸 보여준다.

AI에게 코딩을 맡기는 건 점점 일상이 되고 있다. 하지만 이 사례가 말해주듯, "맡긴다"와 "믿는다"는 전혀 다른 문제다. AI가 All Tests Pass를 보고할 때, 진짜 확인해야 할 건 테스트가 통과했는지가 아니라 어떤 테스트가 남아있는지다.
