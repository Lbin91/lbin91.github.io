클라우드 API에 에이전트를 맡기는 시대가 당분간 계속되겠지만, 최근 로컬에서 에이전트 전체를 돌리려는 시도가 눈에 띄게 늘고 있다. 단순히 모델 하나를 로컬로 올리는 수준이 아니라, 에이전트가 실행되고 권한을 관리하고 여러 모델을 중개하는 런타임 레이어를 직접 구축하려는 움직임이다. r/LocalLLM에서 BubbleHub라는 프로젝트가 올라왔는데, 방향이 흥미해서 정리해봤다.

## 에이전트를 로컬에 두는 것, 실제로 무엇이 필요한가

로컬 LLM 이야기가 나오면 대개 "어떤 모델을 얼마나 빨리 돌릴 수 있나"로 귀결된다. 양자화, VRAM, 토큰 속도. 물론 중요하다. 하지만 에이전트는 단순한 추론기가 아니다. 파일 시스템에 접근하고, 네트워크 요청을 보내고, 외부 API를 호출한다. 클라우드 API를 쓸 때는 이런 권한 문제를 의식하지 않아도 된다. 프로바이더가 알아서 가드레일을 세워두니까. 그런데 에이전트를 로컬에서 직접 운영하면, 그 가드레일을 내가 만들어야 한다.

BubbleHub가 접근하는 방식은 이 문제를 세 단계로 쪼갠다.

첫째, 하드웨어를 감지해서 로컬에서 돌릴 수 있는 모델을 추천한다. 그리고 모델을 따뜻하게 유지(warm)한 채로 여러 에이전트가 동시에 추론 요청을 보낼 수 있게 스케줄링한다. 에이전트마다 모델을 따로 로드하면 메모리가 터지니까, 하나의 모델 인스턴스를 공유하는 구조다. 단순해 보이지만 이게 없으면 로컬에서 에이전트 여러 개를 돌리는 건 현실적으로 불가능하다.

둘째, 각 에이전트를 샌드박스로 격리한다. BubbleHub에서는 이를 "버블"이라고 부른다. 완전히 분리된 오버레이 파일 시스템, 독립된 네임스페이스. 네트워크 트래픽은 런타임 프록시를 통과한다. API 키는 에이전트에게 실제 값을 노출하지 않고, 런타임이 대신 처리한다. 즉 에이전트는 키를 모른 채로 API를 호출하는 구조다.

셋째, 권한이 매니페스트로 관리된다. 에이전트가 매니페스트에 없는 요청을 보내면 차단되고, 사용자에게 승인을 요청한다. 승인된 행동은 매니페스트에 기록되어 다음부터는 자동으로 허용된다. 일회성 승인이 아니라 누적되는 권한 모델이다.

## 왜 이런 구조가 의미 있는가

지금까지 로컬 LLM 프로젝트 대부분은 "얼마나 좋은 모델을 얼마나 빨리 돌릴 수 있느냐"에 집중했다. llama.cpp, Ollama, LM Studio가 그렇다. 훌륭한 도구들이고, 추론 자체는 이제 상당히 성숙했다.

하지만 에이전트는 추론 이후에 행동한다. 파일을 쓰고, 스크립트를 실행하고, 원격 서버에 접속한다. 이 과정에서 권한 제어가 없으면, 에이전트가 실수로 (또는 의도적으로) 시스템에 피해를 줄 수 있다. 클라우드 API에서는 프로바이더가 이 위험을 흡수한다. 로컬에서는 그 안전망이 없다.

BubbleHub의 접근이 흥미로운 이유는, 권한 문제를 "에이전트 매니페스트"라는 명시적 구조로 푼다는 점이다. HTTP 메서드와 URL을 매니페스트와 대조해서 차단 또는 승인을 결정한다. Kubernetes의 네트워크 정책이나 클라우드의 IAM과 비슷한 발상인데, 이걸 로컬 에이전트 런타임에 가져온 것이다.

r/LocalLLM에서 한 댓글 작성자는 "모델을 따뜻하게 유지하면서 작업 전환마다 콜드 스타트를 기다리지 않아도 되는 것만으로도 오래 기다렸다"고 말한다. 동시에 승인 규칙이 얼마나 세밀하게 설정 가능한지 궁금해한다. 당연한 질문이다. 권한 모델의 세밀함이 곧 실사용 가능성을 결정하니까.

## 한계와 남은 과제

BubbleHub가 완성된 답은 아니다. 글쓴이 본인도 "피드백을 찾고 있다"고 말하고, 프로젝트를 계속 밀어나갈 동력이 필요하다고 한다. 다음 목표가 "AI 에이전트 앱 스토어"라는데, OpenClaw 같은 외부 도구를 BubbleHub 안에 설치하면 샌드박스와 API 키 설정이 자동으로 이루어지는 구조를 상상하고 있다.

든든한 이야기이긴 한데, 앱 스토어는 생태계가 뒷받침되어야 작동한다. 지금은 로컬 에이전트 생태계 자체가 초기 단계라서, 당장 마켓플레이스가 활성화되긴 어려울 것이다.

또 하나는 DX(개발자 경험)다. 매니페스트를 어떻게 작성하고, 디버깅은 어떻게 하며, 권한 충돌이 발생했을 때 사용자에게 어떻게 알릴 것인가. 이런 디테일이 실사용을 가른다. 프로젝트가 초기 단계인 만큼, 앞으로 어떻게 다듬어지느냐가 관건이다.

## 같은 흐름의 다른 신호들

오늘 r/LocalLLM에는 DGX Spark 구매를 고민하는 글도 올라왔다. 파인튜닝과 보안 연구용 하네스 개발을 목표로 하는 사용자인데, "이만큼 가치가 있을까"를 묻고 있다. 같은 날 r/ClaudeCode에서는 Claude Code를 활용해 터미널 환경을 통합 관리하는 NodeTerm이라는 오픈소스 프로젝트가 공개되었고, SSH 기반 원격 세션 관리와 터미널 간 컨텍스트 공유 기능을 제공한다.

흩어져 있는 것처럼 보이지만, 방향은 하나로 모인다. 에이전트가 로컬에서, 혹은 로컬에 가까운 환경에서 더 많은 것을 자율적으로 처리하려면 — 추론 성능만으로는 부족하다. 실행 환경의 격리, 권한 관리, 모델 스케줄링, 세션 지속성. 이런 인프라 레이어가 있어야 에이전트가 실수로 시스템을 날리거나 외부에 민감 정보를 유출하지 않는다.

## 정리

로컬 LLM 담론이 "어떤 모델을 돌릴까"에서 "에이전트를 어떻게 안전하게 운영할까"로 넘어가고 있다. BubbleHub는 그 전환점에 있는 프로젝트 중 하나다. 완벽하지 않지만, 풀어야 할 문제를 정확히 짚고 있다.

에이전트를 로컬에서 진지하게 돌리려는 사람이라면, 모델 선택 못지않게 런타임 구조를 고민해야 한다. 누가 파일에 접근할 수 있고, 누가 네트워크를 호출할 수 있고, 그 권한을 누가 승인하는가. 클라우드에서는 보이지 않던 질문들이 로컬에서는 피할 수 없는 과제가 된다.
