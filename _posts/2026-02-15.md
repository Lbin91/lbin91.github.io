OpenClaw는 편했지만, 메인 서버에 설치하기엔 불안했다. 더 안전한 대안을 찾아 나선 이야기.

## OpenClaw, 편하지만 불안하다

홈 서버(M2 맥미니)에서 OpenClaw를 돌리면서 AI 에이전트의 맛을 제대로 봤다. 터미널 명령어를 대신 쳐주고, 간단한 스크립트를 짜주고, 귀찮은 설정 파일을 수정해주는 게 얼마나 편한지.

그런데 문제가 하나 있었다. 보안이다.

OpenClaw는 로컬 파일 시스템에 접근하고 코드를 실행하는 권한이 꽤 강력하다. 이게 편리함의 핵심이기도 한데, 동시에 불안함의 원천이기도 했다. 직접 코드를 읽어봤는데, 파일 접근 전에 권한을 체크하는 로직이 거의 없더라. 메인 컴퓨터에 설치하기엔 찝찝했다.

그래서 지금은 OpenClaw를 "망가져도 상관없는" M2 맥미니에만 격리해서 돌리고 있다. 가벼운 사이드 프로젝트나 실험용 코드 돌릴 때만 쓰는 샌드박스 환경이다.

## 메인 서버에도 비서가 필요해

문제는 내 메인 워크스테이션인 M4 맥미니다.

여기서야말로 복잡한 작업을 처리해 줄 AI 봇이 절실한데, 보안 때문에 OpenClaw를 못 쓰니 답답했다. 코드 리뷰 자동화, 로그 분석, 정기 백업 스크립트 관리 같은 걸 맡기고 싶은데 말이다.

결국 메인 서버에서도 안심하고 돌릴 수 있는, 검증되고 안전하며 커뮤니티가 활발한 대체재를 찾아 나섰다.

## 후보군 탐색

여러 깃허브와 Reddit, Hacker News를 뒤지면서 후보를 추렸다.

### AutoGPT
AI 에이전트의 시조새 격이다. 호기심에 도커로 띄워봤는데, 메모리를 기본 3GB 가까이 잡아먹는다. 간단한 명령어 하나 날리는데도 토큰이 우수수 빠져나가는 게 느껴질 정도였다. "가볍게" 띄워놓고 쓰기엔 부담스러워서 바로 내렸다.

### SuperAGI
엔터프라이즈급 기능을 제공하고 UI도 훌륭하다. 그런데 도커 기반의 복잡한 세팅이 필요했다. 여러 컨테이너를 띄워야 하고, 리소스도 꽤 잡아먹는다. 회사 인프라에서 쓰기엔 좋겠지만, 개인 홈 서버에서 간단히 돌리기엔 조금 과한 느낌.

### LangChain Custom Agent
직접 짜는 방식이다. 자유도는 가장 높지만, 유지보수와 기능 확장을 내가 다 책임져야 한다는 게 걸렸다. 처음 세팅하는 재미는 있겠지만, 나중에 귀찮아질 게 뻔했다.

## 최종 결정: HKUDS/Nanobot

고심 끝에 선택한 건 [HKUDS/nanobot](https://github.com/HKUDS/nanobot)이다.

선택 이유는 명확했다.

- **커뮤니티 규모**: GitHub Stars가 수천 개고, Contributors도 활발하다. 물론 스타 수가 보안을 보장하진 않지만, 최소한 많은 사람이 쓰고 있다는 건 심각한 문제가 방치될 확률이 낮다는 의미다.
- **확장성**: 텔레그램, Slack, Discord 연동은 기본이고, 다양한 LLM 모델을 갈아 끼울 수 있다. GLM, Claude, OpenAI 등 선택지가 넓다.
- **보안 모델**: 여기가 핵심이다. README를 읽어보니 OpenClaw와는 달리 파일 접근 권한을 명시적으로 제한하는 구조다. 명령어 화이트리스트 방식으로 허용된 동작만 실행 가능하고, 샌드박스 모드도 제공한다. OpenClaw가 "모든 걸 할 수 있는 대신 위험한" 구조라면, Nanobot은 "필요한 것만 할 수 있도록 제한하는" 구조에 가깝다.

코드를 몇 개 열어봤더니 실제로 파일 I/O 전에 권한 체크 로직이 여러 번 들어가 있었다. 완벽한 검증은 아니지만, 최소한 "아무 파일이나 마음대로 읽고 쓸 수 있다"는 OpenClaw의 불안함보다는 낫다는 판단이 섰다.

이 정도면 내 소중한 M4 맥미니에 입주시켜도 되겠다는 판단이 섰다.

## 설치는 Git Clone으로

설치 방법은 여러 가지가 있지만, 나는 최신 기능을 바로 당겨 쓰고 싶어서 소스코드 클론 방식을 택했다.

```bash
git clone https://github.com/HKUDS/nanobot.git
cd nanobot
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

"이 정도면 끝 아니야?"라고 생각했다.

그런데 `pip install`이 끝나자마자 뭔가 이상한 경고 메시지들이 주르륵 올라왔다. Python 3.11 버전 이슈인지, 일부 의존성 패키지들이 deprecated 경고를 내뿜고 있었다. 일단 무시하고 넘어갔는데, 이게 나중에 발목을 잡을 줄은...

그리고 설정 파일을 열어보는 순간, "아, 이거 생각보다 복잡하네?" 하는 생각이 들었다. 특히 `config.yaml`의 구조가 생각보다 깊었다. API 키만 넣으면 끝이 아니라, provider 설정, 모델 선택, 권한 범위까지 세세하게 지정해줘야 했다.

이때까지만 해도 나는 앞으로 닥쳐올 "Default Provider" 지옥과 PM2 연동의 시련을 전혀 예상하지 못했다. 그 이야기는 2편에서 이어진다.
